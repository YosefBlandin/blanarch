Inside Blanarch

How the app is put together, why each piece exists, and how the next pieces (steady connections, clear “unsupported server” messages, and IPsec) fit into it. Every diagram names the real files, so you can open them as you read.

Flutter UI Bridge (Pigeon) Engine core Adapters (protocols, mail) Android system

Every claim about a pattern, API or protocol was checked against its original source (official docs, the author, or the RFC) on 28 Sep 2026. Where an earlier explanation was imprecise, the page says so in a red note. Sources are listed at the end.

01

Two programs in one app

Blanarch is a Flutter app for what you see and a Kotlin engine for what the phone does. They talk through a typed contract. The UI never knows how a VPN works, and the engine never knows what a screen looks like.

Flutter · Dart

  • Screens, animation, text in English and Spanish
  • One codebase for Android now and iOS later
  • Golden screenshot tests for every screen
  • Can be closed at any time; the VPN keeps running
Pigeon
commands →
← status, log

Kotlin · Android

  • VpnService: owns the phone's traffic
  • Keystore, notifications, Quick Settings tile
  • A foreground service that outlives the UI
  • TLS, HTTP, PPP, IMAP: the protocol work

Why split it: Android lets only a VpnService create the virtual network card and keep running when the screen is gone. That belongs in native code. Flutter is best at drawing. Each side does what it is good at, and neither can reach into the other.

The Flutter side: MVVM

This follows Flutter's official architecture guide: a UI layer (views and view-models) and a data layer (repositories and services), with an optional domain layer that most apps don't need. Pick a layer to see its job and its files.

intent flows down ↓ · state flows up ↑
Correction. Flutter's guide strongly recommends MVVM, repositories and dependency injection, and recommends Commands one level lower. Result is a design-pattern page in the guide, not a formal recommendation. Flutter ships neither class; Blanarch has its own in lib/utils/. Flutter recommendations · Result pattern

Unidirectional data flow, drawn

The UI never sets “connected”. It asks the engine to connect, and it shows whatever the engine reports. That is why the screen cannot claim “Connected” while the tunnel is down.

03

The bridge: Pigeon

A contract written once in Dart, pigeons/vpn_api.dart, generates matching Dart and Kotlin code. Pigeon is published by the Flutter team and sits on top of platform channels, adding types.

HostApi Dart calls Kotlin

connect(profileId) · disconnect() · submitOtp(code)
probe(address) · saveProfile(p) · useCodeThisTime()
shareText(subject, text) · requestAddTile(always)

Implemented in bridge/VpnBridge.kt, which only translates and forwards.

FlutterApi Kotlin calls Dart

onStatus(VpnStatusMsg) · onLog(LogEntryMsg)
onProfilesChanged(list) · onSetupLink(url)

Received in lib/data/services/vpn_platform.dart and turned into domain models.

Why not hand-written channels: they pass untyped maps, so a typo only fails on a user's phone. With a generated contract the compiler catches it. That is also why the generated *.g.dart and *.g.kt files are never edited by hand. pub.dev/packages/pigeon

04

The engine: ports and adapters

Alistair Cockburn described this in 2005 as hexagonal architecture. The application defines ports (interfaces for what it needs) and the outside world plugs in adapters (real implementations). Blanarch's ports live in one file, vpn/Ports.kt.

Why this shape pays off

Dependency inversion. The orchestrator (high-level policy) depends on interfaces, not on sockets or Android. In Robert C. Martin's words: high-level modules should not depend on low-level modules; both should depend on abstractions.

Testing without a phone. ConnectionOrchestratorTest swaps every adapter for a fake and runs wrong-password, failover, certificate and drop scenarios in milliseconds.

Open for extension. IPsec will be a new adapter behind the same ports. The orchestrator and the screens do not change. That is the open/closed principle.

Two kinds of ports

Cockburn separates driving ports (something calls the app, like the service starting a connection) from driven ports (the app calls out, like signing in to a gateway). Everything in Ports.kt is a driven port. The service and the bridge are the driving side.

Cockburn, Hexagonal Architecture (2005) · Martin, The Open/Closed Principle

06

The connection is a state machine

One immutable VpnStatus snapshot, one phase at a time (state/VpnStatus.kt). Every change is status.update { it.copy(...) }, so nobody ever reads a half-written state. Tap a phase.

Errors are data, not text: ErrorCode is a closed enum with a fatal flag. The orchestrator decides from the flag (a wrong password stops at once; an unreachable server retries), and the UI turns codes into sentences in vpn_texts.dart. Nothing ever matches on error wording, because wording changes and translations differ.

07

Functional core, imperative shell

Gary Bernhardt named this in 2012. Hard logic lives in pure functions that take values and return values. A thin outer shell does the I/O and calls them.

Pure core. LoginProtocol.classifyStep1(response) takes a reply and returns what it means. PppNegotiator even takes now as a parameter instead of reading the clock, so its timers are testable.

Thin shell. SslVpnGateway opens the socket, sends the request, hands the bytes to the core, and acts on the answer. Little is left to go wrong there.

Proof from this week. The gateway answered a wrong password with its HTML login page. We reproduced the exact reply in a pure unit test (RealGatewayReplyTest) in seconds, fixed the core, and never needed the network to prove it.

Bernhardt, Functional Core, Imperative Shell (2012) · Boundaries talk

08

Disconnect = cancel one job

Kotlin coroutines use structured concurrency: every task is a child of the one that started it, and cancelling a parent cancels all its children. The service runs the whole connection as one job, so “Disconnect” is a single job.cancel().

The one trap

Cancellation is cooperative: a coroutine only stops at a suspension point. A blocking Socket.read() never suspends, so it would ignore the cancel and hang.

net/Io.kt's cancellableIo closes the socket when the job is cancelled. The blocked read then throws, and everything unwinds. That is why the project rule says all socket work goes through it.

Correction worth knowing. Kotlin's docs offer runInterruptible() for blocking calls, but a thread interrupt does not wake a classic java.net.Socket read (it only affects NIO interruptible channels). Closing the socket is the correct fix, which is exactly what Blanarch does. Also: withContext(NonCancellable) is for cleanup in finally (our polite logout), never for launching new work. kotlinlang.org · Cancellation and timeouts

One source of truth for status

StatusStore holds a StateFlow<VpnStatus>. A StateFlow always has a value, gives new listeners the latest one, and update { } is atomic. The Flutter screen, the notification and the Quick Settings tile all watch the same store, so they can never disagree.

Two details: the update lambda can run more than once under contention, so it must be pure (it is: just copy). And StateFlow is for state, not events: equal values are not re-sent, and a slow listener can skip steps. That is why the log is a separate stream. StateFlow API

10

Security by design

Secrets

Passwords are encrypted with an Android Keystore key. Keystore keys cannot be exported, and on most phones they live in secure hardware (TEE or StrongBox).

With app lock on, the key is usable only for 60 s after a fingerprint, face or screen-lock check (setUserAuthenticationParameters, Android 11+).

Nuance: removing the phone's screen lock permanently invalidates such keys, so the app must handle KeyPermanentlyInvalidatedException and ask for the password again.

Server identity

Company gateways often use self-signed certificates, and FortiClient's yes/no warning trains people to click through.

Blanarch shows the fingerprint once, then pins its SHA-256 per server and blocks loudly if it ever changes.

This model is trust on first use. OWASP notes the first connection is the weak point, so a fingerprint delivered out of band (the setup link or QR code) is best. A leaf pin breaks when the certificate is renewed; the app then shows the change and asks.

Clean room

The protocol engine was written from our own written spec, never from GPL code, and every step is recorded in PROVENANCE.md. That keeps the App Store open to us.

Rule for every change: spec first, then code, then a provenance line. We followed it for this week's wrong-password fix.

Crypto rule: never write cryptographic primitives yourself. OWASP: “Don't implement your own cryptographic protocols or routines.” We write protocol logic around vetted libraries.

Testing: a pyramid

Many fast tests at the bottom, few slow ones at the top. Mike Cohn popularized the shape in 2009.

Cores catch protocol mistakes. Orchestrator tests with fakes catch sequence mistakes. View-model tests (FakeVpnPlatform) catch UI logic mistakes. Goldens (matchesGoldenFile) catch visual regressions, in light, dark, English and Spanish.

The device is the one thing fakes cannot give. That is why “Connected” was not claimed until you saw it on a real gateway.

Goldens depend on the OS and Flutter version (fonts render slightly differently), so they are regenerated only for intended changes and looked at before committing. Fowler, Test Pyramid

What we build next, and where it plugs in

The order we agreed: steady connections first, then clear “unsupported server” messages, then IPsec. Each one lands in the architecture above without rewriting it.

Step 2 · new event source + policy

Connections that survive drops

  • NetworkWatch (new port): tells the orchestrator the moment Wi-Fi drops or switches, instead of waiting ~30 s for keepalives.
  • SessionPolicy (pure, a strategy object): network changed → rejoin now; no network → new phase WAITING_NETWORK, no attempts burned; session expired → sign in again.
  • Automatic re-sign-in with the saved password and the emailed code.
  • Inline reply in the notification (RemoteInput, Android 7+) feeds the same code pipe the app uses.
  • Alerts: “VPN dropped · reconnecting”, then “Reconnected”.
Step 4 · a smarter probe

Say plainly what we can't serve

  • The setup probe also learns: SSL-VPN tunnel mode switched off (FortiOS 7.6.3+), the server answers IPsec, a client certificate is requested, a host check is required.
  • Each finding is an ErrorCode, so the cause, the fix and “what to tell IT” come through the existing error sheet.
  • The connection is still saved, ready for when IPsec lands.
Step 3 · a second adapter

IPsec behind the same ports

  • New package ipsec/: IKEv2 for sign-in and keys, ESP for packets.
  • Same shape as sslvpn/: pure cores, thin shells.
  • A ProtocolResolver (factory) picks SSL-VPN or IPsec per profile or from the probe.
  • Spec first from public RFCs, then a FortiGate VM trial for traces.
Correction to the drop plan. I first wrote that we'd watch the “default network” and remove NOT_VPN from the request. That is backwards: requests include NOT_VPN by default, which already excludes VPNs. The right tool is registerBestMatchingNetworkCallback (Android 12+) with an internet request, which reports the single best real network. On older versions, registerNetworkCallback reports every matching network and the app picks one. We then tell Android with setUnderlyingNetworks. ConnectivityManager · NetworkRequest.Builder

IPsec, explained from zero

IPsec has two planes. The control plane (IKEv2, RFC 7296) signs you in and agrees on keys. The data plane (ESP, RFC 4303) encrypts every packet with those keys. They map neatly onto our ports.

Anatomy of one ESP packet

Every packet leaving the phone is wrapped like this (RFC 4303). With AES-GCM (RFC 4106), encryption and integrity happen in one step. Tap a field.

sent in the clear encrypted integrity check

Getting through firewalls

NAT traversal (RFC 3948). Both sides hash their addresses into NAT_DETECTION notifications. If a router rewrote them, they move to UDP port 4500 and wrap ESP in UDP. Tiny one-byte keepalives hold the router's mapping open.

TCP when UDP is blocked. IKE and ESP can ride a TCP stream that starts with the bytes IKETCP, each message prefixed by its length. This was RFC 8229; RFC 9329 (2022) replaced it with the same wire format. Fortinet's default TCP mode says it is “RFC 8229 compliant”, usually on port 443. Its other mode (fortinet-esp) is proprietary and only for FortiGate-to-FortiGate.

How Fortinet signs users in

Dial-up IKEv2 authenticates users with EAP inside IKE_AUTH. Fortinet's KB says the default method is EAP-MSCHAPv2, and that MSCHAPv2 is required for users to see a FortiToken prompt or push. EAP-TTLS/PAP is supported for some directories. SAML for IKEv2 arrived in FortiOS 7.2.

Open questions for our spike: how an emailed code is requested, and whether a given gateway authenticates itself with a certificate (as RFC 7296 requires with EAP) or with a pre-shared key, which Fortinet's own examples show.

Fortinet KB: IKEv2 EAP user authentication · Fortinet: ESP within TCP
